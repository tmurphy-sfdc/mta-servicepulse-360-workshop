Lab 1 — Extend the Case Object for Multi-Agency Intake

ServicePulse 360 Workshop v0.7 (revision 10) | Estimated time: 104 minutes | You will create the ServicePulse 360 Lightning App, customize the standard Salesforce Case object (Priority field, Type field) for MTA's multi-agency operations, add two custom fields where standard genuinely can't fit, place those fields on the Lightning record page via Dynamic Forms, and finish by creating a Golden Record you'll use throughout the rest of the workshop.

What you're building and why

MTA's production Salesforce environment (Cassie) runs on the standard Case object. So does almost every Service Cloud implementation. This lab teaches the most common pattern in real-world Salesforce administration: taking standard objects and standard fields and configuring them to match a specific business context. You won't build a parallel custom object. You won't even add custom picklists for things the standard fields can already model. You'll customize the standard picklists' values.

By the end of this lab, your org will have a dedicated ServicePulse 360 Lightning App, four agency-specific Record Types on the standard Case object (NYCT, LIRR, MNR, B&T), the standard Priority and Type picklists customized to MTA's vocabulary (P1 through P4 for Priority, 13 transit-specific values for Type), two custom fields where standard genuinely doesn't fit, a tailored page layout, both custom fields placed on the Lightning record page's canvas via Dynamic Forms, and a Golden Record (a well-populated Case) that you'll use as the central example throughout the rest of the two-day workshop.

Why this mattersThe principle is customize before extending. A custom field is justified only when configuration of the standard field genuinely can't get you there. Not when the default values are wrong. Not when the default label is wrong. In this lab you'll see the test applied four times: twice it produces "customize the standard," twice it produces "add a custom field."

What is "Pronto" and why does my org have restaurant data?

Your workshop org is built on Salesforce's "Pronto" reference environment, a fictitious food-delivery business that uses Salesforce to manage its restaurant partners, menus, deliveries, and customer support. Salesforce ships this org as a hands-on training environment because it has realistic data, configured agents, and pre-built automation. Your job over the next two days isn't to build for Pronto. Your job is to customize the same standard Salesforce platform that runs Pronto's operations to instead match MTA's operations. Wherever you see references to Storefronts, Menus, or Merchant Operations, those are starter content. We'll customize Case to MTA's vocabulary while leaving the starter content alone, the same way Cassie sits on the same Salesforce platform that runs every other Service Cloud in the world.

The decision applied four times

Severity to standard Priority. Standard Priority's values are High/Medium/Low; we need P1 through P4. Wrong values, right field. Customize the picklist values, keep the field standard.
Issue Type to standard Type. Standard Type's values in this org are restaurant-themed. We need transit-specific values. Wrong values, right field. Customize the picklist values.
Resolution Notes to custom field. Standard Case has Description (the original report) but no dedicated resolution-narrative field. No standard field to configure. Add a custom field.
Reported Date/Time to custom field. Standard CreatedDate exists but is read-only and can't be back-dated. Configuration can't make CreatedDate writable. Add a custom field.

What you keep from standard Case unchanged

Subject (short summary line). Standard fits.
Description (full text of the report). Standard fits.
Status (New / On Hold / Escalated / Closed). Standard fits.
Priority (same field, we just change its picklist values).
Type (same field, the new picklist values were pre-deployed; we'll tour those in Part 2.2).
Contact (who reported). Standard fits.
Account (agency or vendor). Standard fits.
Owner, escalation rules, case history, comments: all standard.

P2 - High
P3 - Medium

Part 9 — Place custom fields, Case Record Type, and Asset on the Lightning record page via Dynamic Forms (12 min)

Your custom fields (Reported Date/Time, Resolution Notes) now exist on the Case object, and you added them to the classic Case Layout in Part 6. But the Case Lightning record page in your org is a separate rendering surface that uses Dynamic Forms. Its field sections don't automatically mirror the classic layout. We need to explicitly place Reported Date/Time, Resolution Notes, Case Record Type, AND Asset on the Lightning record page's canvas. Having Case Record Type on the canvas lets users see (and change) which agency a case belongs to without leaving the record page (which Lab 2 will use). Having Asset on the canvas lets users link cases to physical infrastructure (which Lab 3 will use).

Why this mattersThis is where many admins get confused. The classic Case Layout from Part 6 controls several things (field order in the create-record modal, Related Lists, available fields in the Lightning palette), but it does NOT drive the Lightning record page's field display when Dynamic Forms is in use. Dynamic Forms requires you to explicitly place each field as a component on the Lightning record page's canvas.

9.1 — Open a case and launch the App Builder

1.App Launcher then Cases. Click any existing case (if your org has none, come back to Part 9 after Final Verification Check 1 creates one).
2.On the case record page, click the gear icon (top-right) then Edit Page. The Lightning App Builder opens.

9.2 — Add Reported Date/Time to the canvas

1.In the left sidebar, click the Fields tab (next to the Components tab). The Fields panel shows every Case field as draggable items.
2.In the Quick Find box at the top of the Fields panel, type Reported. Reported Date/Time appears in the list.
3.Drag Reported Date/Time onto the canvas. A natural placement is inside the existing Case Details section (if present) or at the top of the main field section.

9.3 — Add Resolution Notes to the canvas

1.In the Fields panel's Quick Find, clear the previous search and type Resolution. Resolution Notes appears.
2.Drag Resolution Notes onto the canvas. Place it near the bottom of the main field area (below Description or in a resolution-related section).

9.4 — Add Case Record Type to the canvas

1.In the Fields panel's Quick Find, clear the previous search and type Record Type. Case Record Type appears.
2.Drag Case Record Type onto the canvas. A sensible placement is near the top of the main field area, so users can see at a glance which agency the Case belongs to.

9.5 — Add Asset to the canvas

1.In the Fields panel's Quick Find, clear the previous search and type Asset. Asset appears.
2.Drag Asset onto the canvas. A sensible placement is in the Case Details section or near Reported Date/Time, so users can see at a glance which Asset the Case is about.

Part 1 - Walk through the standard-fit test (10 min)

Before building, ask whether a standard object could model what we need. Walk through the four candidates:

1.1 - Could the Case object model a service disruption?

Case models an individual customer issue. One rider calls about the G train being suspended. That rider gets a Case. Then another rider calls. Another Case. A disruption affects many riders; each rider gets their own Case. The disruption itself is the parent event, not any single Case. Case cannot model it.

1.2 - Could the Asset object model a service disruption?

Asset models a durable physical thing (a bus, a signal cabin). A disruption is a transient event. The G train line is still there after the signal fault is cleared; the disruption event is over. Different lifecycles. Asset cannot model it.

1.3 - Could a Knowledge article model a service disruption?

Knowledge Article models published informational content: how to use the MetroCard vending machine, FOIL request process, etc. Knowledge Articles have versions and publication states but no operational state lifecycle (declared, active, updated, cleared). Knowledge cannot model it.

1.4 - Could the Work Order object model a service disruption?

Work Order is the repair work. A disruption is the umbrella event that spawns Work Orders (dispatch a tech to fix the signal) AND spawns Cases (rider complaints) AND drives rider-facing communications. Work Order is downstream of the disruption, not the disruption itself. Work Order cannot model it.

1.5 - Conclusion: custom is justified

Why this mattersYou just walked through the standard-fit test for four candidates and ruled all of them out. The test is the real teaching. In production, you apply this same test before building any custom object. If a standard object could do it (even imperfectly), standard wins. If no standard object fits (as here), custom is the right call. In the ServicePulse 360 workshop this is the ONLY custom object we build; everything else is standard. That ratio (one custom to many standard) is a good benchmark for new Salesforce implementations.

Part 1 - Add a Validation Rule to Service Disruption (10 min)

Validation Rules enforce data integrity at save time. In MTA's context: the Operations team needs to measure how long each disruption lasts so leadership can track responsiveness and process efficacy. For that math to work, every disruption needs a Disruption Start Date/Time and a Disruption Cleared Date/Time (both built on Service Disruption in Lab 5), and the Cleared time must be AFTER the Start time (not equal, not before). We'll build the Validation Rule that enforces the ordering.

1.1 - Open the Validation Rules section

1.From Setup, Quick Find: Object Manager, click Object Manager, then click Service Disruption.
2.Click Validation Rules in the left column.
3.Click New.

1.2 - Build the duration-ordering rule

1.Rule Name: Cleared_After_Started.
2.Active: check.
3.Description: Prevents saving a Service Disruption where Disruption Cleared Date/Time is on or before Disruption Start Date/Time. Ensures the operations duration math is always positive.
4.Error Condition Formula: paste the formula below (click Insert Field as needed). The rule fires when this formula evaluates to TRUE.
NOT(ISBLANK(Disruption_Cleared_Date_Time__c)) && NOT(ISBLANK(Disruption_Start_Date_Time__c)) && Disruption_Cleared_Date_Time__c <= Disruption_Start_Date_Time__c
5.Error Message: Disruption Cleared Date/Time must be after Disruption Start Date/Time. Operations duration is measured from Start to Cleared.
6.Error Location: Field (Disruption Cleared Date/Time). This points the error at the specific field so the user knows where to fix it.
7.Click Save.

1.3 - Test the rule

1.App Launcher then Service Disruptions then click SD-00001 (Signal fault on 7 Line, Vernon Blvd).
2.Edit the record. Set Disruption Start Date/Time to the current date and time. Set Disruption Cleared Date/Time to one hour BEFORE the Start time. Click Save.
3.The save fails with your error message pointing at the Disruption Cleared Date/Time field.
4.Correct Disruption Cleared Date/Time to one hour AFTER Disruption Start Date/Time. Click Save. Save succeeds.
Verified? Great job!The Validation Rule enforces data integrity at save time without any code. The MTA Operations team can now trust that every disruption's duration (Cleared minus Started) is a positive number for responsiveness and process efficacy reporting.
